# Architectural Decision: Why Our Cluster Must Use VirtualBox Instead of WSL

This document outlines the technical reasons why our MPI cluster project must be built entirely on **VirtualBox (with Bridged Networking)** rather than **Windows Subsystem for Linux (WSL/WSL2)**. 

While WSL2 is a powerful tool for solo web development, it introduces severe networking barriers that will cause a multi-node MPI cluster to fail.

---

## 1. The Core Network Conflict

An MPI cluster relies on true node-to-node communication. Every machine in the cluster must be able to see, ping, and securely log into every other machine over our phone hotspot network.

### VirtualBox (Bridged Adapter)
* **How it works:** VirtualBox creates a virtual network card that bypasses the Windows operating system and talks directly to the phone hotspot router.
* **The Result:** The hotspot views the VirtualBox VM as a completely independent physical laptop. It assigns the VM its own unique local IP address (e.g., `192.168.43.50`). 
* **MPI Compatibility:** **Perfect.** Every laptop in the group can route data packets directly to this unique IP address without interference.

### WSL2 (Default or Mirrored Mode)
* **How it works:** WSL2 runs inside an isolated utility VM managed by Windows. By default, it hides behind a Network Address Translation (NAT) firewall.
* **The Result:** The phone hotspot cannot see the WSL2 instance; it only sees the main Windows laptop host. WSL2 does not get its own independent IP address on the Wi-Fi network.
* **MPI Compatibility:** **Broken.** If the Master machine tries to send data packets to a WSL2 slave, the phone hotspot will drop the packets because it has no record of the WSL2 internal address.

---

## 2. Technical Breakdown of WSL2 Pitfalls

If a team member attempts to use WSL2 (even with advanced settings like `networkingMode=mirrored`), the project will encounter the following critical failure points:

### A. The Dynamic Port Block (`firewall=true`)
When running a parallel program using `mpirun`, the engines do not communicate over a single standard port. While initial connection happens over SSH (Port 22), OpenMPI dynamically opens **random high-number ports** to fast-track computational data between CPU cores. 

WSL2's mirrored mode forces the use of the Windows Hyper-V firewall (`firewall=true`). Windows security protocols automatically flag and block these unmapped, incoming dynamic ports. This causes the MPI execution to **hang or freeze infinitely** during the handshake phase.

### B. Shared IP Conflict & Port Crashing
In mirrored mode, WSL2 shares the exact network sockets and IP address of the Windows Host. If the Windows host laptop is running common background software (such as Discord, Steam, Spotify, or VS Code server) that occupies ports required by MPI, the cluster execution will immediately crash with a socket binding error.

### C. System Uniformity
For an MPI cluster to function reliably, **predictability is mandatory**. Mixing different virtualization environments means our cluster configuration maps (`/etc/hosts`, SSH authorized keys, and NFS mount targets) would have to be customized entirely differently for each individual machine. 

---

## 3. Comparative Summary

| Feature | VirtualBox (Bridged Mode) | WSL2 (Mirrored/NAT Mode) |
| :--- | :--- | :--- |
| **Network Visibility** | Visible to the entire hotspot network as a separate PC. | Hidden behind the Windows Host system. |
| **IP Allocation** | Receives a unique, dedicated local IP address. | Shares or hides behind the Windows Host IP. |
| **Firewall Behavior** | Bypasses Windows network blocking rules. | Monitored by Hyper-V Windows Firewall. |
| **OpenMPI Stability** | **Stable.** Standard Linux network socket execution. | **Unstable.** Documented socket-mapping bugs. |
| **Storage & RAM Footprint** | Low (4–5 GB space using Ubuntu Server flavor). | Can dynamically bloat Windows host VHDX files. |

## 4. Final Verdict

To guarantee our project works smoothly during the live grading presentation, **all group members must use VirtualBox with a Bridged Network Adapter.** This establishes an equal, open, and standardized network layer across all our physical laptops, allowing us to focus on the parallel code logic rather than troubleshooting Windows network permissions.
